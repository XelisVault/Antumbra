# ADR-011: the Veil cryptographic core

Status: **Proposed**

## Context

The private sphere of the whitepaper (Section 4, steps 1, 2 and 4)
rests on four constructions: one-time destination addresses, Pedersen
commitments, the deterministic shared secret that binds sender and
recipient, and key images. Before any of them can be assembled into a
version 2 transaction, each must be a named, cross-validated routine
with one encoding, one error surface and one archived vector set. The
CryptoNote lineage proved the mathematics for a decade; the danger is
never the theorem, it is the convention: which bytes are hashed, in
which order, reduced how, rejected when. The wallet seed episode of
the zero-defect method (a four-byte endianness convention invisible
to re-reading) is the exact class of fault this layer must
mechanically exclude.

## Decision

A dedicated crate, `antumbra-veil`, holding the cryptographic core
only; the ring signature and the range proof arrive in later
milestones and reuse it. The conventions, frozen here:

1. Curve. Twisted Edwards 25519 (the Ed25519 curve, RFC 8032), the
   same curve the transparent sphere already uses. Group operations
   come from curve25519-dalek (audited, constant time); the
   independent implementation is a from-spec Edwards25519 in Python
   inside the vector generator. Point encoding is the RFC 8032
   compressed form, 32 bytes, little-endian y and the sign of x in
   bit 255.
2. Strict decoding. A point decodes only if the encoding is canonical
   (decompress then recompress must reproduce the exact bytes, which
   excludes the nineteen non-canonical y values), the point is not
   the identity, and the point belongs to the prime-order subgroup,
   the group generated by the standard base point (l P = identity).
   The subgroup rule refuses torsion points and points of mixed
   order in one invariant: a raw decompression can land on both,
   and the torsion attack class on key images opens exactly there.
   A scalar decodes only if the 32 bytes are a non-zero value below
   the group order l. No silent normalization, ever.
3. Hs, the hash to scalar. Keccak-256 of the input, the 32 bytes
   read as a little-endian integer, reduced modulo l. Always
   canonical, always below l.
4. Hp, the hash to point. Hash-and-check with cofactor clearing: for
   a one-byte counter c from 0 to 255, compute Keccak-256 of
   (input, c), interpret the digest as a compressed point; the
   first digest that decompresses canonically names the candidate,
   and the image is eight times that candidate. The multiplication
   by the cofactor places the image in the prime-order subgroup (a
   raw decompression can land on a point of mixed order); a
   candidate of pure torsion clears to the identity and the search
   continues on the next counter. The input of Hp is always public
   (a public key, a protocol tag), so the variable round count
   leaks nothing; each vector records its round count so the map is
   pinned to the bit. The subgroup invariant then holds end to end
   by construction: RFC 8032 public keys are prime order by
   clamping, one-time addresses and commitments are combinations of
   prime-order points, key images are a scalar times the cofactor
   cleared Hp of a point.
5. Wallet scalars. The spend scalar of a seed is the RFC 8032 secret
   scalar (SHA-512 of the seed, first half, clamped) reduced modulo
   l to canonical form; the view scalar applies the same derivation
   to the view seed (Keccak-256 of the spend seed). The reduction
   changes no public key: clamped and reduced differ by a multiple
   of the group order, and the base point has order l.
6. The shared secret. Hs of the compressed encoding of the point
   rA (sender) which equals aR (recipient): one routine,
   `shared_secret(secret, public)`, called with (r, A) by the sender
   and (a, R) by the scanner.
7. The one-time address. P = Hs(rA) G + B, exactly the whitepaper
   equation; the scanner recomputes the same candidate and compares
   in constant time.
8. The one-time secret key and the key image. p = Hs(aR) + b, the
   image I = p Hp(P). The image is deterministic, untraceable to the
   ring member and unlinkable across outputs, and the nullifier
   registry of the ordering layer stores it verbatim.
9. The value generator and commitments. H is Hp of the fixed string
   "ANTUMBRA/veil/value-generator", a nothing-up-my-sleeve point
   with no known discrete log to G. A commitment is C = vH + bG for
   an amount v in atomic units and a blinding scalar b. Homomorphic
   addition holds by construction and is tested.

The archived vector set is produced by
`code/scripts/gen_veil_vectors.py`, which self-checks before writing:
RFC 8032 public keys cross-checked against pycryptodome, the base
point verified against the RFC encoding and the group order,
recipient recovery replayed, homomorphic addition replayed, key
image determinism replayed, and every written point verified inside
the prime-order subgroup. The Rust suite must reproduce every vector
bit for bit, and every invalid vector (non-canonical point, torsion
or mixed order point, non-canonical scalar) must be rejected with
the matching error.

## Discarded options

Monero's ge_fromfe hash to point (a dedicated rational map, more
uniform in one pass, but requires porting a subtle field-arithmetic
routine into both implementations instead of reusing the RFC 8032
decompression both already have); deriving Veil scalars from the seed
by Keccak alone (breaks the binding to the published address keys);
allowing non-canonical scalars in arithmetic (the exact class of
convention fault the method exists to exclude).

## Required validation

The full vector set of `antumbra-veil` reproduced bit for bit by the
independent Python implementation; the wallet scalar public keys
equal to the Ed25519 public keys of the primitives crate; rejection
tests on every invalid encoding; the regeneration job of the
continuous integration reproducing the committed vectors byte for
byte.
